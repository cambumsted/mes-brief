Making the grid live

Four options for moving the AMEX partnership grid from a hand-coded HTML table to a live data surface — ordered low to high effort.

Archived working note — originally part of the partnership-ideas page. Kept for reference. The live partnership grid is on Partnerships reporting.
Option 1

Stay manual, refresh on a cadence

Effort: Low

Keep the grid as it is. After each campaign closes, someone (likely us) opens each regional Excel file, copies the totals, and updates the HTML. ~30 min per region per quarter.

Cost: $0 Latency: Days to weeks after campaign close IT involvement: None
Developer view
What it actually is

The current state — a hand-coded HTML table with hard-coded values and per-cell data-src-* attributes for provenance tooltips. No backend, no auth, no data pipeline.

Tradeoffs
  • Zero infrastructure cost and zero maintenance burden between refreshes.
  • Refresh is gated on a human remembering to do it; cadence drifts as people get busy.
  • Data lineage is documented inline (the tooltip cells already point at sheet + cell ranges), which makes the manual refresh fast — but it doesn't catch sheet restructures.
  • Fine for a working draft / leadership preview. Not a long-term answer if the grid becomes a primary decision surface.
Option 2

Owners publish a flat data file, page reads it

Effort: Low–Medium

Each regional owner (or a shared script) exports their Excel to a simple CSV/JSON file in a known location. The HTML page reads that file each time it loads. Same grid you have today — just sourced from a file rather than typed in.

Cost: $0 Latency: Hours after owner exports IT involvement: Minimal
Developer view
Architecture

Three JSON files committed to the repo (one per region) + a single fetch() on page load that hydrates the grid from those files. The existing data-src-* attributes become the data contract — the JSON keys map to the same metric / region / market shape.

What it takes to build
  • Define a minimal JSON schema: { region, period, markets[{ name, offer, enrollments, redemptions, ... }] }.
  • Write a one-shot PowerShell script (or Excel macro) per region that reads the workbook and emits the JSON — ~30 lines each. The Excel-COM extractor we already ran for analysis is 80% of this.
  • Refactor the grid HTML into a template that fetch()es and renders. ~150 lines of vanilla JS.
  • Decide where the JSON lives: committed to the GitHub repo (publishes on push), or hosted in SharePoint and fetched cross-origin (needs CORS / shared link).
Tradeoffs
  • Still no auth, still works on GitHub Pages.
  • Reliance on regional owners running the export. If they don't, the page silently shows stale data — needs a "last refreshed" timestamp on the grid.
  • Sheet restructures still break things, but break them in JS at render time (visible) rather than in a tooltip (hidden).
Option 3

Read the Excel files directly via Microsoft Graph

Effort: Medium–High

Microsoft has an API (Graph) that can read live Excel files in SharePoint and return the cell values. The grid would call that API on load — whatever's in the spreadsheets right now is what shows up. No human exports, no stale data. Requires IT approval and some auth plumbing.

Cost: $0–10/month Latency: Real-time IT involvement: Entra app registration, tenant consent
Developer view
Architecture

Graph exposes workbook ranges as JSON via endpoints like GET /drives/{drive-id}/items/{item-id}/workbook/worksheets/{name}/range(address='D5:S55'). Two auth patterns:

  • Delegated — each viewer signs in with their Microsoft account; the page calls Graph with their token. Keeps the site fully static. Best for an internal-only leadership tool. MSAL.js handles the flow.
  • App-only — a service principal reads the files on a schedule (Azure Function on a timer) and writes a cached JSON to the site. Viewers never authenticate. Tiny server-side piece required.
What it takes to build
  • Entra ID app registration (Marketing IT / IT ticket — typically 1–2 week SLA).
  • Tenant admin consent for Files.Read.All or scoped Sites.Selected.
  • Move from GitHub Pages → Azure Static Web Apps (free tier; supports Entra-protected routes and Functions natively). The existing staticwebapp.config.json in the repo means we're already partway set up.
  • ~200 lines of JS for Graph calls and parsing; another ~100 for token handling if going delegated.
Tradeoffs
  • Genuinely live — no stale data, no human in the loop.
  • Cell-address-based reads break if a row gets inserted upstream. Mitigation: lock layout via a data contract, or address by named ranges / Excel Tables instead of cell coordinates.
  • Auth-protected sites have higher friction for sharing — every viewer needs an MS account that has permission to the source files (which they probably do, but worth confirming).
Option 4

Build a Power BI model, embed the report

Effort: High

Pipe the three regional files into a Power BI dataset with scheduled refresh, model the metric definitions as DAX, build visuals, and embed the report in the brief page. Numbers stay live; the narrative wrapper stays in HTML.

Cost: Existing Power BI Pro licenses Latency: Up to refresh schedule (typically daily) IT involvement: Workspace + gateway setup
Developer view
Architecture

Power BI Desktop ingests the three Excel files via SharePoint connectors. A semantic model unifies them: shared dimensions (region, market, period), conformed metric definitions in DAX, and the comparability footnotes baked in as calculated columns or report-level annotations. Publishes to a Power BI workspace; scheduled refresh runs daily; the report is embedded in the brief via <iframe> using the "Publish to web" or "Embed for your organization" flow.

What it takes to build
  • 2–3 weeks for the data model: connectors, transformations in Power Query, DAX measures for the shared metric definitions, region/market dimensional model.
  • Workspace + scheduled refresh setup (data gateway not needed if files live in SharePoint Online).
  • Embed code generation; iframe drop-in to the partnership-ideas page.
  • Ongoing model ownership — someone needs to maintain DAX when sheet shapes drift.
Tradeoffs
  • Strongest for the live-numbers job: Power BI is purpose-built for this and handles refresh, caching, and visual interactivity natively.
  • Weak fit for everything else this page does — the narrative, the metric definitions table, the per-cell provenance tooltips, the "what's not comparable" footnotes. Those don't translate to Power BI native experiences.
  • Best as the data layer behind a hybrid: Power BI for the grid visual, HTML for the wrapper. The two embedded together is what gets you the leadership-ready surface.

Pragmatic path: stay on Option 1 through the next 1–2 partnerships joining the grid. If leadership is actually consulting it, move to Option 2 to prove auto-refresh adds adoption value. Only graduate to Option 3 or 4 once we know the grid is a primary decision surface AND the regional sheet formats are stable enough to act as a data contract.
